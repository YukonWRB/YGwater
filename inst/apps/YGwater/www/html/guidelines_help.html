Guideline SQL Helper

AquaCache stores water quality guideline values in the criteria schema. Most guidelines should use fixed values, lookup ranges, lookup grids, one-input formulas, narrative rows, or external model result rows. Use an SQL scalar rule only when the guideline derivation cannot be represented cleanly by those structured rule types.

SQL scalar rules are still database-driven. The Shiny app stores the SQL in criteria.guideline_value_rules.formula_sql, and the database evaluates it through the same guideline views and functions used by reports, plots, and scripts.

Rules for SQL Scalar Rules

  • Write one PostgreSQL statement beginning with SELECT or WITH ... SELECT.
  • Return exactly one numeric value in the database units for the target parameter.
  • Use $1::integer when the expression needs the current sample_id.
  • Do not include a semicolon, inserts, updates, deletes, DDL, temp tables, or session changes.
  • Return NULL::numeric when required sample inputs are missing and no valid guideline value can be derived.

Useful Database Helpers

When a SQL scalar uses sample chemistry, list the same chemistry rows under Rule inputs first, then use the Insert input button to add those helper calls to the SQL editor. The admin form checks discrete.get_sample_val() and criteria.get_sample_hardness() calls against those rows before saving.

HelperUseExample
criteria.get_sample_hardness(sample_id) Returns preferred hardness as mg/L CaCO3 using the database's standard priority order. criteria.get_sample_hardness($1::integer)
discrete.get_sample_val(...) Fetches a sample result by parameter, fraction, and optional speciation. discrete.get_sample_val(sample_id := $1::integer, parameter_id := 1190::integer, sample_fraction_id := NULL::integer)

Fixed Value

Prefer the structured fixed-value rule type for this case, but this is the equivalent SQL scalar form: 

SELECT 0.230::numeric

Hardness-Dependent Example

This pattern is useful for guidelines that depend on hardness and cannot be represented by the one-input formula rule. 

WITH vals AS (
  SELECT criteria.get_sample_hardness($1::integer) AS hardness_mg_l_caco3
)
SELECT CASE
  WHEN hardness_mg_l_caco3 IS NULL THEN NULL::numeric
  WHEN hardness_mg_l_caco3 < 82 THEN 0.002::numeric
  WHEN hardness_mg_l_caco3 <= 180 THEN
    (0.2 * exp(0.8545 * ln(hardness_mg_l_caco3) - 1.465) / 1000)::numeric
  ELSE 0.004::numeric
END
FROM vals

Multiple Sample Inputs

SQL scalar rules can combine several inputs. Keep parameter, fraction, and speciation IDs explicit so the stored rule remains reproducible. 

WITH vals AS (
  SELECT
    criteria.get_sample_hardness($1::integer) AS hardness_mg_l_caco3,
    discrete.get_sample_val(
      sample_id := $1::integer,
      parameter_id := 538::integer,
      sample_fraction_id := 2::integer,
      result_speciation_id := NULL::integer
    ) AS doc_mg_l
)
SELECT CASE
  WHEN hardness_mg_l_caco3 IS NULL OR doc_mg_l IS NULL THEN NULL::numeric
  ELSE (0.001 + 0.00002 * hardness_mg_l_caco3 + 0.0001 * doc_mg_l)::numeric
END
FROM vals

Testing SQL Scalar Rules

The Shiny tester can evaluate a saved guideline against either an existing result ID or a temporary sample. Temporary tests insert a synthetic sample and result rows inside a transaction, run criteria.applicable_guidelines_for_result(), and then roll the transaction back.

For BLM or other external-model guidelines, enter the sample chemistry in the temporary input table and optionally enter an external model output. The app stores that model output only for the duration of the test transaction.

SQL scalar rules are intentionally powerful. Use structured rule types first when they fit, and keep SQL scalar expressions short, reviewed, and tied to source documentation.
